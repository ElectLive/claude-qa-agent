# session-report

Apply in the main session at the end of WAY 1 (Phase 5) or WAY 2 (Phase 4).
Everything it needs is already in context, so it runs inline:
- Environment URL (WAY 1) or API base URL + spec source (WAY 2)
- `test-execution-agent`'s results YAML. Each entry has `status`, `page`, `a11y: { checked, violations }`, and for API scenarios the `api-responses/` capture
- Bugs filed in this session: ref, title, labels (from the `bug-report` skill + `tracker`)

## Where it goes

1. Save to `./qa-artifacts/sessions/session-<YYYY-MM-DD-HH-MM>.md` (WAY 1) or `./qa-artifacts/sessions/api-<YYYY-MM-DD-HH-MM>.md` (WAY 2)
2. Print it to chat
3. WAY 1: file it as an issue labeled `qa-session-report` (`issue.create`, per `tracker`), with the same body

## WAY 1 template

Build the Accessibility Report by grouping results on their `page` field and
counting violations by `impact`.

```markdown

**Date:** [ISO date]
**Environment:** [URL]
**Triggered by:** [Feature name or issue ref]

---

## Test Execution Summary

| Status | Count |
|---|---|
| ✅ Passed | N |
| ❌ Failed | N |
| ⚠️ Blocked | N |
| ⏭️ Skipped | N |
| **Total** | **N** |

---

## Failed / Blocked Test Cases

| Test | Title | Status | Failure point | Artifact |
|---|---|---|---|---|
| Test#02 | Login rejects invalid password | ❌ fail | Step 3 — no error message shown | runs/<id>/artifacts/… |

---

## Not Filed as Bugs

| Test | Why | Follow-up |
|---|---|---|

| Test#06 | 🧊 quarantined (flaky) | tracked in <flaky-test ref> |

(or "none")

---

|---|---|---|---|---|

**A11y bugs filed:** #N (sev-2), …   (or "none")
```

## Rules
- Always include the Accessibility section in WAY 1 reports, even when it shows 0 violations, and the Schema/Performance sections in WAY 2 reports, even when empty ("none")
- Counts must add up: Passed + Failed + Blocked + Skipped = Total
- Always list artifact paths
- Always end with the watermark footer (CLAUDE.md's Output Watermark). It is part of both the saved file and the filed issue body
