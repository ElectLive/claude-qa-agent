# DevOps QA Agent

An autonomous QA agent for DevOps-oriented teams. Give it a GitLab Issue, a staging URL, or a failing CI/CD pipeline — it writes test cases, executes them in a real browser, tests your APIs, runs accessibility checks, and files bugs to GitLab Issues, all without you lifting a finger.

> Built with Claude Code · Playwright + playwright-bdd · GitLab MCP · MIT licensed

[![validate](https://github.com/GhassenAZZOUZ/claude-qa-agent/actions/workflows/validate.yml/badge.svg)](https://github.com/GhassenAZZOUZ/claude-qa-agent/actions/workflows/validate.yml)

**Quick start:** [Setup](#setup) · **Modes:** [Sixteen Modes](#sixteen-modes) · **Help wanted:** [Roadmap](#roadmap) · [Contributing](CONTRIBUTING.md)

## What Makes This Different

| | Typical QA Agent | This Agent |
|---|---|---|
| Bug tracking | Jira (paid) | **GitLab Issues** (free, native to your repo) |
| Test management | Qase (paid SaaS) | **Local markdown files + GitLab Issue labels** |
| Browser tests | E2E only | E2E **+ accessibility (axe) built into every scenario** |
| API testing | None | **`api it` mode — OpenAPI validation + functional tests** |
| CI diagnosis | None | **`ci it` mode — GitLab CI/CD pipeline failure root cause analysis** |
| After a bug is filed | Nothing | **`verify it` runs the bug's regression test and closes or reopens it** |
| Tests in the pipeline | Manual | **`ci setup` exports the suite + validated GitLab CI jobs** |
| Broken selectors | Re-write by hand | **`heal it` repairs renamed/moved elements from Playwright's failure snapshot** |
| Flaky tests | File bogus bugs | **`flaky` finds them across runs and quarantines them** |

## Output Watermark

Every GitLab issue, GitLab comment, and saved markdown report this agent produces ends with:

```
🤖 Generated by DevOps QA Agent — review before acting on this.
```

Every generated `.feature`/`.steps.ts` test file starts with the same attribution as a header comment. This makes AI-generated content clearly identifiable to anyone on the team who opens an issue, a report, or a test file — useful once the agent is shared beyond a single user. The exact wording is defined once in `CLAUDE.md`'s **Output Watermark** section; sub-agent templates in `.claude/agents/` include it directly rather than relying on the caller to add it afterward.

## Sixteen Modes

Each mode ("WAY") is a skill in `.claude/skills/`. Type a trigger phrase, or `/<skill>` directly. Only the triggered WAY's instructions are loaded.

| WAY | Skill | Trigger | What happens |
|---|---|---|---|
| 1 | `e2e-session` | `e2e it` | Requirements → browser tests (+a11y) → run → heal locator failures → file bugs → session report |
| 2 | `api-session` | `api it` | OpenAPI → API tests → run (schema, perf) → file bugs → API report |
| 3 | `quick-bug` | `report it` | One-line bug → GitLab issue + a regression test |
| 4 | `write-tests` | `write it` | Requirements → test files + `test-plan` issue, no run |
| 5 | `diagnose-ci` | `ci it` | Failed pipeline → failure type, root cause, concrete fix |
| 6 | `enhance-story` | `analyze us` | Score a story → rewrite with Gherkin ACs, scenarios, DoD → QA analysis comment |
| 7 | `benchmark` | `benchmark it` | App/URL/repo → sourced competitor matrix (+ Lighthouse) |
| 8 | `gap-stories` | `gap it` | Benchmark → leader → gap user stories |
| 9 | `verify-fix` | `verify it #142` | Run the bug's regression test → `verified`/`fix-failed`, close/reopen |
| 10 | `ci-test-setup` | `ci setup` | Export the suite to the app repo + GitLab CI jobs (JUnit, artifacts), linted |
| 11 | `mr-impact` | `test mr !87` | MR diff → only the affected tests → results + coverage gaps on the MR |
| 12 | `release-readiness` | `release check v2.3` | Bugs, QA results, pipeline, untested stories → GO / GO WITH RISKS / NO-GO |
| 13 | `flaky-triage` | `flaky` | Last N runs → flaky tests → quarantine + `flaky-test` issues |
| 14 | `traceability` | `trace it #148` | AC → tests → latest result → open bugs matrix |
| 15 | `load-test` | `load test` | k6 smoke/load/stress/spike/soak with p95 + error-rate thresholds (never prod) |
| 16 | `heal-tests` | `heal it` | Repair tests broken by UI renames, with approval |

## Setup

### 1. Prerequisites

| Requirement | Version |
|---|---|
| [Claude Code](https://claude.com/claude-code) | Latest (any surface: terminal, VS Code, JetBrains, desktop) |
| Node.js | 20+ |
| A GitLab project + access token | gitlab.com or self-hosted, scope `api` |
| Optional: k6 or Docker | For WAY 15 |

### 2. Get the agent

```bash
git clone https://github.com/GhassenAZZOUZ/claude-qa-agent.git
cd claude-qa-agent
```

Use this folder as your QA workspace: open Claude Code here. The tests it writes go to `qa-artifacts/`, which is gitignored. `ci setup` (WAY 10) exports them into your app's repo when you want them in a pipeline.

### 3. Install the test runner

```bash
cp -r runner-template/. qa-artifacts/
cd qa-artifacts && npm install && npx playwright install chromium && cd ..
```

### 4. Configure

```bash
cp .env.example .env
cp .mcp.example.json .mcp.json
cp .claude/settings.example.json .claude/settings.json
```

Fill in the same values in all three: your GitLab token, URL and project ID, plus your staging/prod/feature URLs.

> **Why three files?** `.env` is read by your shell. `settings.json` passes env vars to Claude Code and its MCP servers. `.mcp.json` declares the GitLab MCP server. All three are gitignored.

### 5. Verify

Start Claude Code in the folder and type `/mcp`: `gitlab` should show as connected. Then try a mode that doesn't need GitLab:

```
write it "Users can reset their password from the login page via an emailed link" App: https://staging.myapp.com
```

## Usage Examples

### WAY 1 — Full E2E Session

```
e2e it --env staging
Feature: User Login
Requirements:
1. Users log in with email + password
2. Invalid credentials show an error message
3. Successful login redirects to /dashboard
4. Locked accounts show a specific locked message
```

From a GitLab Issue:
```
e2e it --env staging
Issue: #42
```

### WAY 2 — API Testing

From an OpenAPI spec:
```
api it --env staging
Spec: https://api.staging.myapp.com/openapi.json
```

Specific endpoints only:
```
api it --env staging
Endpoints:
- POST /api/users
- GET /api/users/{id}
- DELETE /api/users/{id}
```

### WAY 3 — Quick Bug Report

```
report it
Auth, Logged in as standard user, Go to /settings > Click Delete Account > Confirm > Observe: 500 error instead of success message
```

### WAY 4 — Write Test Cases

```
write it
Issue: #55
App: https://staging.myapp.com/upload
Spec: https://api.staging.myapp.com/openapi.json#/paths/~1upload
MR: 88
```

### WAY 5 — Diagnose CI Failure

```
ci it
Run: https://gitlab.com/your-group/your-project/-/pipelines/12345678
```

Or:
```
ci it
Project: your-group/your-project
Pipeline ID: 12345678
```

### WAY 6 — User Story Enhancer

```
analyze us #143
```

Or equivalently:
```
enhance us #143
analyze and update us #143
improve us #143
```

The agent scores the story out of 100, rewrites the issue body with Gherkin acceptance criteria, test scenarios, and a Definition of Done checklist, then posts the score + QA findings as a separate comment so the body stays clean for developers.

### WAY 7 — Competitor Benchmark

```
benchmark it https://github.com/org/my-app --focus features,perf
benchmark it https://myapp.com --max 8
find competitors "self-hosted test management tool"
```

Accepts an app URL, a name/description, or a Git repository (GitHub/GitLab URL or local path). For a repo, features are derived from the code as well as the README and tagged `code-verified` vs `readme-claimed`. Every cell in the comparison cites a source; anything not found is `❓`, never guessed. Private repos are cloned with `GITHUB_TOKEN`/`GITLAB_TOKEN` from `.env`.

### WAY 8 — Benchmark Gap → User Stories

```
gap it
gap it qa-artifacts/benchmarks/finance-2026-10-10.md --scope market --repo https://github.com/org/my-app
gap it --leader PocketSmith --max 5
```

Reads a WAY 7 report and ranks competitors with a visible weighted score (feature coverage 40, overlap 20, evidence confidence 15, market fit 15, measured quality 10). It picks the leader worth matching, not just the most similar one, and writes one user story per feature the leader has that the target lacks. `❓` cells are never treated as gaps. With a repo given, each gap is grepped first so no story is written for something that already exists. Gaps that contradict a deliberate product choice are flagged `decision-needed`.

### WAY 9 — Verify Fix

```
verify it #142 --env staging
verify all --close
```

Runs `test-cases/regression/bug-<IID>/` (written by WAY 3). A pass gets a comment and the `verified` label, and the issue is closed with your OK. A fail gets a comment with the screenshot and the `fix-failed` label, and the issue is reopened if it was closed.

### WAY 10 — CI Test Setup

```
ci setup ../my-app
```

Copies the runnable suite from the gitignored `qa-artifacts/` into `my-app/qa-tests/` (never `.auth/`, `runs/` or `node_modules`), writes `.gitlab/ci/qa-tests.gitlab-ci.yml` (a Playwright image pinned to your version, JUnit report, artifacts, and a manual baseline-update job), lints it with GitLab, and lists the CI variables to create. It never commits or pushes.

### WAY 11 — MR Test Impact

```
test mr !87 --env feature/discount-codes
```

`mr-test-impact` maps the diff (routes, endpoints, labels, linked issues) to existing tests, then only those run. The MR gets one comment: selected tests with the reason each was picked, the results, heals needed, and the changed areas with no test.

### WAY 12 — Release Readiness

```
release check "v2.3" --min-pass 95
```

Open bugs by severity, `fix-failed` bugs, the latest QA results for the milestone's features, the latest pipeline, untested stories, and quarantined tests are combined into GO / GO WITH RISKS / NO-GO, with every signal sourced. It's a recommendation; the team decides.

### WAY 13 — Flaky Triage

```
flaky --window 15
```

`flaky.mjs` aggregates the last N `results.json`. A test that flips pass ↔ fail with the same error each time is proposed for `@quarantine` plus a `flaky-test` issue. Quarantined tests keep running but stop producing bugs, and are proposed for unquarantine after 10 straight passes.

### WAY 14 — Traceability

```
trace it #148
```

Each AC of the story → the tests whose `**Covers:**` line names it → their latest result → open bugs. Untested `must` ACs get an offer to write tests.

### WAY 15 — Load Test

```
load test spec=https://api.myapp.com/openapi.json profile=load --env staging
```

Writes k6 scripts (read-only endpoints by default) and always runs a smoke pass. It asks before running the real profile. Threshold breaches can be filed as `performance` bugs. `--env prod` is refused.

### WAY 16 — Heal Tests

```
heal it
```

Reads Playwright's `error-context.md` (the page snapshot at the moment of failure) for each locator failure in the latest run, proposes the minimal step/Gherkin change, and applies it with your OK, re-running to confirm. It never changes expected values; an element that's truly gone is a bug, not a heal.

## What the Agent Produces

**WAY 1 (E2E session):**
- `qa-artifacts/test-cases/[feature]-[date]/Test#<nn>.{md,feature,steps.ts}` — one Gherkin + playwright-bdd triple per test case, plus an index `.md`
- `qa-artifacts/runs/[timestamp]/results.json` — execution results, including each scenario's built-in accessibility check
- `qa-artifacts/runs/[RUN_ID]/artifacts/…` — failure screenshot, trace, `error-context.md`; console/network logs inside `results.json`
- `qa-artifacts/sessions/session-[timestamp].md` — full session summary
- GitLab Issues: one `test-plan` issue + one `test-case` issue per test case + one `bug` issue per failure + one `qa-session-report`

**WAY 2 (API session):**
- `qa-artifacts/test-cases/[api-slug]-[date]/Test#<nn>.{md,feature,steps.ts}` — API test cases, same triple format
- `qa-artifacts/api-responses/[endpoint]-[method]-[timestamp].json` — full req/resp capture
- `qa-artifacts/sessions/api-[timestamp].md` — API session summary
- GitLab Issues: one `bug` + `api` issue per failure

**WAY 3 (Quick bug):**
- GitLab Issue: one `bug` issue with full reproduction steps
- `qa-artifacts/test-cases/regression/bug-<IID>/Test#01.{md,feature,steps.ts}` — regression test reproducing it, tagged `@regression`

**WAY 4 (Write test cases):**
- `qa-artifacts/test-cases/[feature]-[date]/Test#<nn>.{md,feature,steps.ts}` — E2E + API test cases, same triple format
- GitLab Issue: one `test-plan` issue
- Optional MR discussion comment with test plan summary

**WAY 5 (CI diagnosis):**
- `qa-artifacts/ci/ci-[run-id]-[date].md` — root cause report
- Optional MR discussion comment with the diagnosis

**WAY 6 (User story enhancer):**
- GitLab Issue body — replaced with enhanced story (Gherkin ACs, test scenarios, DoD, original preserved in collapsible)
- GitLab Issue comment — QA analysis report (score/100, grade, strengths, issues found with severity + suggestions)

**WAY 7 (Competitor benchmark):**
- `qa-artifacts/benchmarks/[target]-[date].md` — fingerprint, competitors, feature matrix, pricing, OSS repo health, differentiators/gaps, sources
- `qa-artifacts/benchmarks/raw/*.json` — raw Lighthouse runs (when `perf`/`a11y` focus)
- Optional GitLab Issue labeled `benchmark`

**WAY 8 (Benchmark gap → user stories):**
- `qa-artifacts/benchmarks/stories/[target]-[date]/index.md`: leader ranking, backlog, decision-needed, already-implemented
- `qa-artifacts/benchmarks/stories/[target]-[date]/US-<n>.md`: one user story per gap
- Optional GitLab Issues: one `user-story` + `benchmark-gap` issue per story, plus a `benchmark` index issue

**WAY 9–16:** verify report + issue comments/labels (9) · `qa-tests/` + CI include in the app repo (10) · MR comment + `sessions/mr-*.md` (11) · `releases/<milestone>-<date>.md` (12) · `@quarantine` tags + `flaky-test` issues + `sessions/flaky-*.md` (13) · `traceability/<IID>-<date>.md` (14) · `load-tests/<api>-<date>/` scripts + summaries (15) · healed test files + `sessions/heal-*.md` (16)

## Sub-Agents Reference

All 9 sub-agents live in `.claude/agents/`. They are invoked automatically by the orchestrator — you never call them directly. Work that only applies a rubric or template to data the main session already holds is a **skill** instead (see Skills Reference below) — no sub-agent cold start, no isolation needed. The actual GitLab issue/comment filing mechanics (create/update/comment, label conventions, failure handling) live in a shared skill, `.claude/skills/gitlab-filing/SKILL.md`, referenced by every agent below that produces content destined for GitLab.

---

### `test-writer`
**Used by:** WAY 1, WAY 2, WAY 3 (regression test), WAY 4

The single test-authoring agent for the whole project — first analyzes the requirements into happy path / negative / edge / boundary / security / permission scenarios (mandatory input, ID, upload and numeric checks), then writes **both** browser and API scenarios, always as a `Test#<nn>.{md,feature,steps.ts}` triple: Gherkin `.feature` + a real `playwright-bdd` step-definition file (`page` fixture for UI, `request` fixture for API). Every UI scenario that navigates gets a built-in accessibility step (`@axe-core/playwright`, WCAG 2.0 A/AA + best-practice) — there's no separate a11y pass. Every API scenario is tagged `@api` and gets at least 9 mandatory cases per endpoint (happy path, auth failures, missing/invalid fields, IDOR, schema validation, perf threshold; +3 for POST/PUT). Replaces the former `e2e-test-writer`, `api-test-writer`, and `integration-test-writer`.

---

### `test-execution-agent`
**Used by:** WAY 1, WAY 2

The single test-execution agent — runs every `.feature`/`.steps.ts` pair `test-writer` produces via real `npx bddgen && npx playwright test`, across 2 projects (`e2e`, `api`). No live-driven MCP session: it runs compiled, repeatable Playwright suites. Checks the user's config against a documented contract first (a missing project is a setup error), captures screenshot/console/network log on any `FAIL`/`BLOCKED`, re-runs only network-failed scenarios once (never assertion failures), and surfaces each scenario's accessibility step result inline with its pass/fail. Replaces the former `playwright-navigator`, `api-executor`, and `accessibility-checker`.

---

### `test-healer`
**Used by:** WAY 1, 9, 11, 16

Works from Playwright's `error-context.md`, which holds the failing locator and the page's accessibility snapshot at the moment of failure, so no browser or MCP server is needed. It classifies each locator failure as healable (renamed/moved), ambiguous, or not healable (element missing → likely a product bug), proposes the minimal `.feature`/step change, and in apply mode edits and re-runs the one scenario. It never touches expected values or `@visual` baselines.

---

### `mr-test-impact`
**Used by:** WAY 11

Fetches an MR's changed files and only the diffs it needs, extracts routes, endpoints, UI labels and linked issues, and matches them against `Test#<nn>` steps and traceability lines. Returns a ranked selection with honest confidence, plus the changed areas no test touches.

---

### `load-test-writer`
**Used by:** WAY 15

Writes k6 scripts per profile (smoke/load/stress/spike/soak) with per-endpoint tags and p95/error-rate thresholds, read-only by default, with credentials only from `__ENV`. It always runs smoke, runs heavier profiles only on explicit confirmation, and never runs against prod.

---

### `ci-diagnostician`
**Used by:** WAY 5

Fetches the pipeline, failed jobs (trace tail first), and linked MR diff itself via GitLab MCP — so large logs stay in its context, not the main session's — then classifies the failure into one of five types (`test-failure / build-failure / infra-failure / config-failure / dependency-failure`). Quotes the exact failing log line, cross-references the MR diff, states confidence (HIGH/MEDIUM/LOW), and gives a specific fix recommendation (file + line or command). Marks transient failures as retry-safe.

---

### `user-story-enhancer`
**Used by:** WAY 6

Fetches a GitLab Issue and scores the user story out of 100 (deductions for missing business value, vague language, absent ACs, no error handling, no NFRs, etc.). Updates the issue body with: enhanced "As a / I want / So that" story, AC summary table with priorities, full Gherkin Given/When/Then scenarios in a collapsible block, test scenarios covering all six types (happy_path, edge_case, negative, boundary, security, performance), open questions that block testing, and a DoD checklist. Posts the QA analysis (score, grade, strengths, issues with severity + concrete suggestions) as a **separate comment** to keep the body clean for developers. The original story is always preserved verbatim inside a collapsible block.

## Skills Reference

Skills live in `.claude/skills/` and run inline in the main session.

### `bug-report`
**Used by:** WAY 1 Phase 4, WAY 2 Phase 3, WAY 3 (`/bug-report`)

Classifies a bug with a fixed Sev-1–4 × P1–3 matrix and hard auto-escalation rules (XSS/IDOR/auth bypass/injection → Sev-1; PII exposure → Sev-2 minimum; payment failure → Sev-1; axe critical/serious → Sev-2), picks labels, parses the WAY 3 shorthand, and formats the developer-ready issue body. Replaces `severity-classifier` + `bug-reporter`.

### `session-report`
**Used by:** WAY 1 Phase 5, WAY 2 Phase 4

Builds, saves, and (WAY 1) files the session summary — counts, failed tests, per-page a11y table or API schema/performance flags, bugs filed. Replaces `session-reporter`.

### `gitlab-filing`
**Used by:** every GitLab create/update/comment/upload

Tool names, parameters, toolsets, label conventions, attachments (`upload_markdown`), close/reopen, failure handling.

### `user-story-format`
**Used by:** `user-story-enhancer` (WAY 6), `benchmark-gap-story-writer` (WAY 8)

The single story body definition (story, Gherkin ACs, scenarios, Missing Information, DoD), so WAY 6 can re-score WAY 8's stories and `test-writer` can trace tests to stable AC IDs.

### WAY skills
The 16 WAY skills hold each mode's full procedure; see **Sixteen Modes** above.

## Troubleshooting

| Problem | Fix |
|---|---|
| GitLab MCP 401 error | Check `GITLAB_TOKEN` in `.env` and `settings.json`; verify the token scope includes `api` (or `read_api`/`write_repository`) |
| `test-execution-agent` fails to launch tests | Run `npx playwright install chromium` and confirm `npx playwright --version` works — it runs the toolchain locally via Bash, not through an MCP server |
| Agent goes off-task | Ensure `CLAUDE.md` is in the project root; reload VS Code window |
| Screenshots not saved | Config needs `use: { screenshot: 'only-on-failure', trace: 'retain-on-failure' }`; they land in `runs/<RUN_ID>/artifacts/` |
| `bddgen`: "Function has 2 arguments, but expected 0-1" | A step takes `testInfo` as a 2nd parameter; use `async ({ page, $testInfo }) => …` instead |
| `bddgen`: "Multiple definitions matched" | The same step is defined twice; keep generic steps only in `steps/` |
| Visual tests fail in CI but pass locally | Baselines are OS-specific; run the `qa-update-baselines` job and commit its output |
| WAY 15 writes scripts but doesn't run | Install k6 or Docker (`grafana/k6`) |
| GitLab MCP server not connecting | Type `/mcp` in Claude Code panel to verify server status |

## Roadmap

Help wanted. Open a "New WAY / feature" issue to discuss first.

- **GitHub Issues & Jira support.** GitLab is the only tracker today. All tracker calls go through the `gitlab-filing` skill, so a `github-filing` / `jira-filing` skill with the same contract is the cleanest path
- **Exploratory tester.** Explore an app with no requirements and report bugs and untested flows (needs a browser-driving MCP server scoped to that agent)
- **Claude Code plugin packaging.** Install with one command instead of cloning
- **More trigger languages.** French, Spanish, German, Portuguese… trigger phrases in the skill descriptions
- **Mobile.** Appium or Maestro runner alongside Playwright
